Every page on this site is available to an agent over the Model Context Protocol. An assistant
with this connected searches the documentation and quotes it, instead of recalling an endpoint
that may not exist.

## How do I connect it?

<InstallTabs pkg="@thepulseapi/docs-mcp" />

<Callout title="Not on npm yet">
  The package is being published. Until then, run it from source: clone
  `mypulseapi/handbook`, then `cd mcp && npm install`, and point your client's `command` at `node`
  with the full path of `server.mjs`. [Open source](/opensource) has the steps.
</Callout>

Or point your client at it directly, with no install:

```json title="claude_desktop_config.json"
{
  "mcpServers": {
    "pulse-docs": {
      "command": "npx",
      "args": ["-y", "@thepulseapi/docs-mcp"]
    }
  }
}
```

The same block works in Claude Code (`.mcp.json`), Cursor and anything else that speaks MCP over
stdio.

<Callout title="It runs on your machine, not ours">
  This site is a static export, so there is no server here to host an HTTP endpoint on. The
  package runs wherever your agent runs and fetches the published documentation index, which
  means nothing about your prompts or your code reaches us. The one exception is
  `resolve_products`, which sends its own input to the PULSE API, and only once you set a key.
</Callout>

## What tools does it expose?

| Tool | What it does |
| --- | --- |
| `search_docs` | Full-text search across every page. Returns the matching section, its URL and a score |
| `get_page` | One page as Markdown, by path, such as `/quickstart` or `/api/v1/audit` |
| `list_pages` | Every page with its title, for orienting before a search |
| `resolve_products` | Which candidates meet the shopper's requirements, which fail, and which the listing cannot tell, with what is missing. Needs an API key |

The three docs tools take a `lang` of `en` or `vi`.

## How does an agent decide with it?

An agent asked to recommend a product has two bad options without it: recommend from what it
thinks it read, or refuse. `resolve_products` gives it a third: say exactly what the listings
show. It calls [`POST /decide`](/api/v1/decide), so add your key to the config:

```json title=".mcp.json"
{
  "mcpServers": {
    "pulse": {
      "command": "npx",
      "args": ["-y", "@thepulseapi/docs-mcp"],
      "env": { "PULSE_API_KEY": "pk_live_..." }
    }
  }
}
```

Ask *"which of these laptops have at least 16GB of RAM and cost under $1,500?"* and the agent
gets, per laptop, `fits`, `fails` or `cannot_tell`, with the missing facts named. A product
whose listing never states its RAM is reported as exactly that, rather than guessed into the
answer or silently dropped. Each call counts as one decision on your plan.

## Why is the search lexical rather than semantic?

The website embeds your question with a model it has already downloaded. Making an agent download
one to ask a question is a poor trade, because the agent is itself a language model: it can read
three candidate sections and decide which is right far better than a cosine can.

It also matters that an agent asking about `/catalog/audit` wants the page containing that exact
string, and lexical scoring is precise about that where an embedding blurs it.

## What if I want it pointed somewhere else?

Set `PULSE_DOCS_ORIGIN` to serve from a different origin, which is mostly useful when you are
working on the documentation itself:

```bash
PULSE_DOCS_ORIGIN=http://localhost:3000 npx @thepulseapi/docs-mcp
```

## Can I just read the Markdown?

Yes, and you do not need MCP for it.

| | |
| --- | --- |
| [`/llms.txt`](/llms.txt) | Every page, titled and linked, in one file |
| [`/llms-full.txt`](/llms-full.txt) | The whole documentation as one Markdown document |
| `/llms.mdx/docs/<path>/content.md` | Any single page as Markdown |
| [`/search-index.json`](/search-index.json) | The chunked corpus with its embeddings |

Each page also carries a **Copy Markdown** button, which is the fastest route when you just want
to paste one page into a conversation.
