---
title: Audit a catalogue
description: POST /catalog/audit and /catalog/verify, which grade catalogue data rather than rank it.
icon: ClipboardCheck
---

The ranking endpoints answer "which products first". These two answer a different question:
**can this catalogue answer the questions shoppers are asking of it at all.**

Both take a CSV as a string in the body rather than a file upload. An audit is a pure function
over text, so multipart would add a parser, a temporary file and a cleanup path for no gain at a
size where a category export is tens of kilobytes.

Neither call stores anything unless you ask it to.

## `POST /catalog/audit`

```bash
curl -X POST "https://api.thepulseapi.com/api/v1/catalog/audit" \
  -H "Content-Type: application/json" \
  -H "x-api-key: pk_live_..." \
  -d '{
    "csv": "id,category,size,material\n1,helmet,L,abs\n2,helmet,,\n",
    "source": "merchant",
    "amortisationHorizon": 5000
  }'
```

<Callout title="Why the horizon is not guessed for you">
  Without it the response carries no `action`. Comparing "ask the shopper" against "record the
  fact once" needs to know how many shoppers the fact would serve, and picking a number on your
  behalf would bury the assumption the whole comparison rests on.
</Callout>

### Evidence states and repair actions

Every response carries `evidence`: for each product and attribute that cannot be answered, what
kind of gap it is and the action that closes it, plus a count per attribute in `byAttribute`.
Columns named like a title or description (`name`, `title`, `description`) are read as the
product's own text rather than as attributes.

| State | What it means | Action |
|---|---|---|
| `missing` | Not recorded, and not in the product's text | `record`, or `compute` when a `derivations` input is known |
| `buried` | Not in the field, but the title or description holds a value this attribute takes elsewhere (`found`) | `show` |
| `invisible` | Recorded, but not in `filterable`, so no shopper can filter on it | `show` |
| `unresolved` | A value exists but is too weak or too old to decide on | `ask` |
| `conflicting` | Equally trusted sources disagree | `reconcile` |
| `not-observable` | No product records it and no text mentions it | `abstain`: an answer should say it cannot tell |

Two actions are not gaps. `generate` marks a recorded fact the product's text never mentions, so
copy can be written from it rather than invented. `dont-fix` replaces the action on an attribute
whose repair would barely change what a question can rule out.

### Revenue exposure

Add a `revenue` column, or `price` and `units_sold`, and the response carries `revenue`: the
category's total, the revenue on products with at least one gap worth fixing (`withGaps`), on
products nothing can find (`unresolvable`), and per attribute in `byAttribute`, largest first. It
adds up your own figures; it is not a forecast of what a repair would earn. `units_sold` and
`revenue` are not treated as attributes; `price` still is, because a budget is a requirement.
Amounts such as `20.990.000` and `20,990,000` both read correctly.

## `POST /catalog/verify`

The same request does two jobs. Send `before` and `after` on their own and it is a monitor: what
changed between two exports, with nothing claimed. Add `repairs` and the same diff grades the
claims.

```bash
curl -X POST "https://api.thepulseapi.com/api/v1/catalog/verify" \
  -H "Content-Type: application/json" \
  -H "x-api-key: pk_live_..." \
  -d '{
    "before": "id,category,size\n1,helmet,\n",
    "after":  "id,category,size\n1,helmet,L\n",
    "repairs": [{ "attribute": "size", "method": "manual", "actualHours": 3 }],
    "category": "Helmets"
  }'
```

  Monitor and verification are the same computation over the same diff. The only difference is
  whether anything was claimed about it.
</Callout>
