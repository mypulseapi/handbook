PULSE publishes **two separate interfaces**, and they are not the same size.

  `@thepulseapi/sdk` has a method for six of the thirteen endpoints. Everything else, including

  rather than the [SDK reference](/sdk).

## The product surface

Every row below is reachable with a publishable key and the `x-api-key` header. Nothing here
needs a login.

| Endpoint | What it is for | Counts toward usage | SDK method |
| --- | --- | --- | --- |
| `POST /track` | Signals in, personas out | Yes | `track()` |
| `POST /track/behavior` | One named behaviour | Yes | none |
| `POST /track/keywords` | A raw search query, extracted for you | Yes | none |
| `POST /session` | The personas inferred so far | Yes | `getSession()` |
| `POST /catalog/ranked` | Rank the catalogue PULSE holds | Yes | `rankedCatalog()` |
| `POST /search` | Rank products you pass in | Yes | `search()` |
| `POST /rerank` | Reorder a result set from your own engine | Yes | none |
| `POST /suggest` | Query suggestions, scored on the session | **No** | none |
| `POST /catalog/audit` | What a catalogue cannot answer | Yes | none |
| `POST /catalog/verify` | What a repair actually changed | Yes | none |
| `POST /event` | A named outcome | **No** | `event()` |
| `POST /exposure` | What was actually rendered | **No** | `exposure()` |
| `POST /outcomes` | What happened to each order line: kept, returned, cancelled. From your server | **No** | none |

### Return history is not an endpoint

There is no return-history call. It is two optional fields you add to each product you already
send to `/search`, `/rerank` or `/catalog/ranked`:

- `deliveredOrders`: how many orders of the product were delivered.
- `evidenceReturns`: how many of those came back for a reason better product information could
  have prevented, such as wrong size or not as described.

Send them and the ranking also weighs how often a product stays bought. Leave them out and
ranking is exactly what it would otherwise be. If you report each order line to
[`POST /outcomes`](/api/v1/outcomes) instead, PULSE keeps these counts for you and you send
neither. The rules for counting are in [Return history](/api/v1/ranking#return-history).

### Why four of them are free

`/event`, `/exposure` and `/outcomes` are how you prove the ranking worked. Charging for measurement makes
switching it off the rational move, which blinds the learning loop and destroys the value case
in the same stroke.

`/suggest` fires on every keystroke. Metering it like `/search` would bill per character typed,
so someone spelling out a query would pay ten times for one search.

<Callout title="Usage is grouped by the first path segment">
  `/track` and `/track/behavior` are both billed as `track`, and `/catalog/ranked`,
  `/catalog/audit` and `/catalog/verify` are all billed as `catalog`. Your invoice shows a line
  per operation rather than one total, because `/search` costs real compute and `/session`
  costs almost nothing.
</Callout>

Audit, Verification and Monitor are **one computation over a diff**. There is no third endpoint
for Monitor because there is no third thing to compute: the only difference is whether anything
was claimed about the change.

## What is not on this page

There is a second, much larger API behind a **JWT**, not an API key: organizations, users,
roles, API keys, catalogue management, billing and subscriptions. That is the management plane
the [merchant portal](https://app.thepulseapi.com) is built on. It is not metered, it is not
sold as a product, and it is not documented here yet.

<Callout type="warn" title="Treat anything undocumented as unsupported">
  Routes exist that are not on this page. Some are internal, some are reachable only with a
  login, and some resolve at the gateway and are not served downstream. If it is not written
  down here, do not build on it.
</Callout>
